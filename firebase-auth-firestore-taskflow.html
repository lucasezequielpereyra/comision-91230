Sección 1

El flujo de autenticación: dos árboles, una sola app

En React Native no protegemos una URL: decidimos qué árbol de navegación existe según el estado de la sesión.

En una aplicación web es común pensar en una ruta privada envuelta por un componente como <ProtectedRoute>. En TaskFlow móvil vamos a resolver el problema de otra manera: renderizando condicionalmente el árbol de navegación.

Si Redux conoce un usuario autenticado, mostramos el flujo privado de la aplicación. Si no hay usuario, mostramos el flujo público de Login y Registro. La consecuencia es importante: una pantalla privada no queda simplemente "bloqueada"; directamente no forma parte del árbol actual. 

export default function AppNavigator() {
  const user = useAppSelector(state => state.auth.user)
  const isLoading = useAppSelector(state => state.auth.isLoading)

  if (isLoading) {
    return <SplashScreen />
  }

  return (
    <NavigationContainer>
      {user ? <MainNavigator /> : <AuthNavigator />}
    </NavigationContainer>
  )
}

La idea importante

La navegación protegida mejora la experiencia y evita caminos inválidos dentro de la app. La autorización real de los datos se resuelve en otro nivel: las Security Rules de Firebase.

Sección 2

Persistencia de sesión: abrir la app sin volver a loguearse

La sesión de Firebase y el estado de Redux cumplen funciones distintas: Firebase conserva la identidad; Redux permite que la UI reaccione.

El listener onAuthStateChanged es el puente entre Firebase Authentication y nuestra aplicación. Cuando TaskFlow arranca, Firebase resuelve si existe una sesión activa y ejecuta el callback con un usuario o con null. A partir de ahí sincronizamos el estado de Redux. 

useEffect(() => {
  const unsubscribe = onAuthStateChanged(auth, (firebaseUser) => {
    if (firebaseUser) {
      dispatch(setUser({
        uid: firebaseUser.uid,
        email: firebaseUser.email,
      }))
    } else {
      dispatch(clearUser())
    }

    dispatch(setAuthLoading(false))
  })

  return unsubscribe  // limpiar el listener al desmontar
}, [dispatch])
Firebase Authentication

Es la fuente que nos informa si existe una sesión y quién es el usuario autenticado.

Redux

Expone esa información al resto de la UI para que navegación, pantallas y servicios puedan reaccionar.

Sección 3

Firestore: de un array local a una fuente de datos compartida

Redux sigue siendo útil para la interfaz, pero las tareas dejan de nacer y morir solamente en memoria.

Hasta este punto, TaskFlow puede tener un array de tareas dentro del store. Eso funciona mientras el proceso de la aplicación sigue vivo. En este checkpoint, la fuente persistente pasa a ser una colección de Firestore llamada tasks.

Colección

tasks agrupa todos los documentos de tareas.

Documento

Cada tarea tiene su propio ID y sus campos.

Propietario

userId relaciona cada tarea con el usuario autenticado.

La consulta que separa los datos por usuario

const tasksQuery = query(
  collection(db, 'tasks'),
  where('userId', '==', currentUser.uid)
)

const unsubscribe = onSnapshot(tasksQuery, (snapshot) => {
  const tasks = snapshot.docs.map(doc => ({
    id: doc.id,
    ...doc.data(),
  }))

  dispatch(setTasks(tasks))
})
Filtro no significa seguridad

El where(...) hace que la app pida las tareas correctas. Pero un cliente modificado podría intentar otra consulta. La separación real entre usuarios debe reforzarse con Security Rules.

Sección 4

CRUD en Firestore: crear, leer, actualizar y borrar

Cada interacción que antes cambiaba solo Redux ahora debe producir un cambio persistente.

Acción en TaskFlowFirestoreIdea clave
Crear tareaaddDoc()Agregar userId del usuario activo.
Leer tareasquery() + where()Pedir solamente las del usuario autenticado.
Escuchar cambiosonSnapshot()Actualizar Redux cuando cambia la colección.
Completar / editarupdateDoc()Modificar el documento persistido, no solo la UI.
EliminardeleteDoc()Eliminar por ID de documento.

Crear

const createTask = async (taskData, userId) => {
  return addDoc(collection(db, 'tasks'), {
    ...taskData,
    userId,
    completed: false,
    createdAt: serverTimestamp(),
  })
}

Actualizar

const toggleTask = async (task) => {
  const taskRef = doc(db, 'tasks', task.id)

  await updateDoc(taskRef, {
    completed: !task.completed,
  })
}

Borrar

const removeTask = async (taskId) => {
  const taskRef = doc(db, 'tasks', taskId)
  await deleteDoc(taskRef)
}

Sección 5

Sincronización con Redux: quién es la fuente de verdad

En este checkpoint, Redux representa el estado actual de la interfaz; Firestore conserva el estado persistente.

La idea más limpia es evitar que una misma operación tenga dos historias independientes. Si hacemos un dispatch(addTask(...)) y además un addDoc(...) sin coordinación, corremos el riesgo de que la UI muestre algo que Firestore rechazó o de que la nube cambie sin reflejarse localmente.

Un authSlice mínimo

const initialState = {
  user: null,
  token: null,
  isLoading: true,
  error: null,
}

const authSlice = createSlice({
  name: 'auth',
  initialState,
  reducers: {
    setUser: (state, action) => {
      state.user = action.payload
    },
    clearUser: (state) => {
      state.user = null
      state.token = null
    },
    setAuthLoading: (state, action) => {
      state.isLoading = action.payload
    },
  },
})
Redux Toolkit y "mutación"

En los reducers de Redux Toolkit podemos escribir state.user = ... porque internamente utiliza Immer. No contradice la inmutabilidad que vimos en React: Redux Toolkit genera el estado inmutable resultante por nosotros.

Sección 6

Errores comunes y seguridad real

Una aplicación conectada agrega problemas que no existían cuando todo era un array local.

Error 1 · No limpiar listeners

Los listeners de onAuthStateChanged y onSnapshot permanecen activos hasta que los desconectamos. Si el componente se monta varias veces y nunca limpiamos, podemos terminar con callbacks duplicados y fugas de memoria.

useEffect(() => {
  const unsubscribe = onSnapshot(tasksQuery, handleSnapshot)
  return unsubscribe
}, [tasksQuery])
Error 2 · Confiar solamente en la interfaz

Que el usuario no tenga una pantalla o un botón no significa que los datos estén seguros. La app cliente está en manos del usuario. Las Security Rules deben impedir que una cuenta acceda a documentos ajenos.

Error 3 · No manejar la asincronía

Login, registro y operaciones de Firestore devuelven Promises. Una app robusta debe representar cargando, éxito y error, en lugar de asumir que toda operación termina correctamente.

Ejemplo conceptual de reglas por propietario

match /tasks/{taskId} {
  allow read, update, delete: if request.auth != null
    && resource.data.userId == request.auth.uid;

  allow create: if request.auth != null
    && request.resource.data.userId == request.auth.uid;
}
