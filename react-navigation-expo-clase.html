Sección 1

El modelo mental: navegar no es renderizar condicionalmente

En la clase anterior podíamos simular una navegación con selectedTask. React Navigation toma esa idea y la convierte en un sistema de navegación completo.

Una pantalla normal responde a un estado: "si selectedTask existe, muestro el detalle". Eso sirve para entender el concepto, pero una aplicación real necesita mucho más: saber qué pantallas fueron visitadas, permitir volver, animar transiciones, mostrar headers, manejar gestos, mantener historiales independientes y representar estructuras como tabs dentro de un stack.

Tres palabras que conviene separar
  • Screen: el componente React que representa una pantalla.
  • Route: la entrada de navegación que identifica esa pantalla dentro de un navigator.
  • Navigator: el sistema que administra rutas, historial, transiciones y UI de navegación.
Una aclaración para Expo

Esta guía usa React Navigation directamente: @react-navigation/native y los navegadores específicos. Expo también ofrece Expo Router, que está construido sobre React Navigation pero usa rutas basadas en archivos. Son dos formas distintas de organizar una aplicación. No conviene mezclarlas mentalmente: en esta clase vamos a aprender el modelo explícito de React Navigation.

Sección 2

Instalación en un proyecto Expo

React Navigation está dividido en un núcleo y varios navegadores. Instalamos solamente lo que vamos a usar.

1. Núcleo y dependencias base

npm install @react-navigation/native

npx expo install react-native-screens react-native-safe-area-context

@react-navigation/native aporta el núcleo de React Navigation. Los navegadores se instalan por separado. En Expo conviene usar npx expo install para las dependencias nativas porque Expo selecciona versiones compatibles con el SDK instalado.

2. Native Stack + Bottom Tabs

npm install @react-navigation/native-stack
npm install @react-navigation/bottom-tabs

3. Drawer

npm install @react-navigation/drawer

npx expo install \
  react-native-gesture-handler \
  react-native-reanimated \
  react-native-worklets
¿Por qué aparecen Gesture Handler, Reanimated y Worklets?

El Drawer depende de gestos y animaciones nativas. react-native-gesture-handler maneja la interacción de arrastre; Reanimated y Worklets permiten ejecutar la lógica de animación de forma adecuada. Si aparecen errores relacionados con worklets, Reanimated o módulos nativos, normalmente hay una instalación/configuración incompatible.

El punto de entrada

import { NavigationContainer } from '@react-navigation/native'

export default function App() {
  return (
    <NavigationContainer>
      {/* Acá vive el navigator raíz */}
    </NavigationContainer>
  )
}
Regla de oro

En una aplicación con React Navigation directo, normalmente existe un NavigationContainer raíz. No necesitás envolver cada navigator en otro NavigationContainer.

Sección 3

Stack Navigator: una pila de pantallas

El Stack representa el flujo más intuitivo: abrís una pantalla encima de otra y luego volvés.

Pensalo literalmente como una pila de platos. Arrancás con Home. Cuando navegás a Detail, la nueva pantalla se coloca arriba. Si navegás a Edit, queda otra encima. Al hacer back, se retira la pantalla superior. 

import { createNativeStackNavigator } from '@react-navigation/native-stack'

const Stack = createNativeStackNavigator()

function AppStack() {
  return (
    <Stack.Navigator>
      <Stack.Screen name="Home" component={HomeScreen} />
      <Stack.Screen name="Detail" component={DetailScreen} />
      <Stack.Screen name="Edit" component={EditScreen} />
    </Stack.Navigator>
  )
}

Navegar y volver

import { Button } from 'react-native'

function HomeScreen({ navigation }) {
  return (
    <Button
      title="Ver detalle"
      onPress={() => navigation.navigate('Detail')}
    />
  )
}

function DetailScreen({ navigation }) {
  return (
    <Button
      title="Volver"
      onPress={() => navigation.goBack()}
    />
  )
}
navigate() no significa simplemente "renderizá este componente"

Estás enviando una acción al navigator. El navigator decide cómo cambia su estado. Esa diferencia conceptual es importante: la pantalla no controla directamente qué componente se dibuja; le pide al navigator que cambie de ruta.

Sección 4

Parámetros: llevar información a otra pantalla

Una navegación normalmente necesita contexto: ¿qué usuario? ¿qué producto? ¿qué tarea?

La forma habitual es navegar indicando el nombre de la ruta y un objeto de parámetros. La pantalla destino recibe esos parámetros desde route.params. 

navigation.navigate('Detail', {
  taskId: task.id,
})
function DetailScreen({ route }) {
  const { taskId } = route.params

  return (
    <View>
      <Text>Tarea: {taskId}</Text>
    </View>
  )
}
Preferible: pasar un ID
navigate('Detail', {
  taskId: task.id
})

El detalle puede consultar la fuente de verdad y obtener el dato actualizado.

Cuidado: pasar objetos grandes
navigate('Detail', {
  task: task
})

Es válido en casos simples, pero puede generar datos desactualizados si el objeto cambia en otro lugar.

Params no son almacenamiento global

Un parámetro sirve para transportar información relacionada con una ruta. No es una sustitución de Context, Redux, Zustand o una base de datos. Si una información debe ser compartida por muchas partes de la aplicación, conviene que exista una fuente de verdad apropiada.

No pongas cualquier cosa en params

Evitá usar params como depósito de estado de la aplicación, especialmente para objetos enormes, funciones o estructuras que deberían vivir en otro lugar. Para navegación, lo más robusto suele ser que los params describan qué recurso estamos viendo, por ejemplo userId o productId.

Sección 5

Bottom Tabs: las áreas principales de la aplicación

Tabs no reemplaza al Stack. Cumplen problemas diferentes y normalmente trabajan juntos.

Las Bottom Tabs son apropiadas cuando una aplicación tiene varias áreas principales que el usuario puede cambiar rápidamente: Inicio, Buscar, Favoritos, Perfil. Cada tab representa una ruta y tiene su propio estado de navegación. 

import { createBottomTabNavigator } from '@react-navigation/bottom-tabs'

const Tab = createBottomTabNavigator()

function MainTabs() {
  return (
    <Tab.Navigator>
      <Tab.Screen name="Home" component={HomeScreen} />
      <Tab.Screen name="Search" component={SearchScreen} />
      <Tab.Screen name="Profile" component={ProfileScreen} />
    </Tab.Navigator>
  )
}

Regla práctica

Si algo es una sección principal de la aplicación → probablemente Tab. Si algo es una pantalla dentro de una sección → probablemente Stack.

Sección 6

Drawer Navigator: navegación lateral

El Drawer agrega un menú lateral que se abre mediante un gesto o un botón.

Es útil cuando hay muchas secciones secundarias o cuando el menú ocupa demasiado espacio para estar permanentemente visible en tabs. El usuario puede abrirlo y elegir una ruta. 

import { createDrawerNavigator } from '@react-navigation/drawer'

const Drawer = createDrawerNavigator()

function AppDrawer() {
  return (
    <Drawer.Navigator>
      <Drawer.Screen name="Home" component={HomeScreen} />
      <Drawer.Screen name="Settings" component={SettingsScreen} />
      <Drawer.Screen name="Help" component={HelpScreen} />
    </Drawer.Navigator>
  )
}
Demo conceptual

Un Drawer es otro Navigator

Abrí el menú y cambiá de pantalla. En una app real, el gesto de arrastre abre/cierra el Drawer.

Controlar el Drawer desde una pantalla

function HomeScreen({ navigation }) {
  return (
    <Button
      title="Abrir menú"
      onPress={() => navigation.openDrawer()}
    />

Drawer y Tabs no son intercambiables

Las tabs están pensadas para cambiar frecuentemente entre áreas principales. El Drawer está pensado para descubrir/acceder a secciones desde un menú lateral. Una aplicación puede usar ambos, pero hay que definir claramente qué nivel de navegación representa cada uno.

Sección 7

Navegación anidada: donde realmente empieza la aplicación real

Stack, Tabs y Drawer no son tres opciones excluyentes. Se pueden combinar.

Una arquitectura frecuente es tener un Drawer raíz, dentro una sección principal con Tabs, y dentro de cada tab un Stack. El secreto para no perderse es preguntar siempre: ¿qué navigator es el padre de esta ruta?

Ejemplo de estructura

NavigationContainer
└── DrawerNavigator
    ├── MainTabs
    │   ├── HomeStack
    │   │   ├── Home
    │   │   └── Detail
    │   └── ProfileStack
    │       ├── Profile
    │       └── EditProfile
    └── Settings
La pregunta correcta ante un problema de navegación

No preguntes solamente "¿por qué navigate() no funciona?". Preguntá: "¿en qué navigator está registrada la ruta que quiero abrir?". Esa pregunta suele revelar el problema inmediatamente.

Sección 8

Back, historial y comportamiento de cada navigator

"Volver" no significa exactamente lo mismo en un Stack, un Tab y un Drawer.

SituaciónQué representaAcción típica
Stack volver a la pantalla anterior navigation.goBack()
Stack ir a una ruta concreta navigation.navigate('Home')
Stack reemplazar la pantalla actual navigation.replace('Home')
Drawer abrir/cerrar menú openDrawer() / closeDrawer()
Tabs cambiar de sección navigate('Profile')

push() vs navigate()

// navigate: busca una ruta existente según el comportamiento
// del navigator y puede llevarte a ella.
navigation.navigate('Detail', { taskId })

// push: agrega otra instancia de la ruta al Stack.
navigation.push('Detail', { taskId })
Ejemplo de bug

Si una pantalla hace push('Detail') cada vez que el usuario toca un botón, podés terminar con Home → Detail → Detail → Detail. El usuario tendrá que apretar Back varias veces. La decisión entre navigate, push y replace debe representar el flujo real de la aplicación.

Después del login: replace

// Login → Home
navigation.replace('Home')

La intención suele ser que el usuario no vuelva al login apretando Back. Para flujos de autenticación más completos, es preferible que el árbol de navegación dependa del estado de autenticación y no intentar controlar todo con una cadena de replace().

Sección 9

Headers, Safe Area y quién controla el espacio

Navegar no es solamente cambiar de pantalla: los navegadores también pueden dibujar UI alrededor de ella.

Opciones del Stack

<Stack.Navigator
  screenOptions={{
    headerShown: true,
    headerStyle: {
      backgroundColor: '#211710',
    },
    headerTintColor: '#fff',
  }}
>
  <Stack.Screen
    name="Home"
    component={HomeScreen}
    options={{
      title: 'Inicio',
    }}
  />
</Stack.Navigator>

screenOptions permite definir valores comunes para muchas pantallas. options permite personalizar una pantalla específica. Esta distinción evita repetir configuración en cada Screen.

Safe Area

Los teléfonos modernos tienen zonas que no deberían quedar tapadas por el notch, Dynamic Island, barra de estado o indicadores del sistema. React Native ofrece SafeAreaView y, para casos más flexibles, useSafeAreaInsets(). 

import { useSafeAreaInsets } from 'react-native-safe-area-context'

function CustomScreen() {
  const insets = useSafeAreaInsets()

  return (
    <View style={{
      paddingTop: insets.top,
      paddingBottom: insets.bottom,
    }}>
      {/* contenido */}
    </View>
  )
}
No agregues padding "a ojo"

Un paddingTop: 50 puede verse bien en un teléfono y mal en otro. Cuando el problema está relacionado con el área segura del dispositivo, usá los insets reales.

Otra regla importante

Si el navigator ya administra un header, no construyas otro header manualmente sin entender quién está ocupando el espacio. Muchos problemas de "contenido debajo del header" son simplemente una doble administración del layout.

Sección 10

Autenticación: navegación pública y privada

El login no debería ser simplemente una pantalla más dentro del mismo árbol de navegación.

Una aplicación suele tener dos mundos: rutas que cualquier usuario puede visitar y rutas disponibles solamente cuando existe una sesión válida. 

function RootNavigator() {
  const { session } = useAuth()

  return (
    <NavigationContainer>
      {session ? <AppNavigator /> : <AuthNavigator />}
    </NavigationContainer>
  )
}
Ventaja

Un usuario sin sesión no necesita que todas las pantallas privadas estén "protegidas" con ifs. Esas rutas directamente no forman parte del árbol activo.

Sección 11

Deep linking: entrar directamente a una pantalla

Una aplicación real no siempre empieza en Home: puede abrirse desde una notificación, un enlace o un QR.

El deep linking permite mapear URLs o esquemas de aplicación a rutas de React Navigation. Por ejemplo, un enlace conceptual como miapp://tasks/42 podría llevar directamente al detalle de la tarea 42. 

const linking = {
  prefixes: ['miapp://', 'https://miapp.example'],
  config: {
    screens: {
      Home: '',
      Detail: 'tasks/:taskId',
    },
  },
}

<NavigationContainer linking={linking}>
  <AppNavigator />
</NavigationContainer>
Por qué esto importa

Deep linking obliga a pensar la navegación como rutas reales y no como simples botones. También afecta notificaciones push, autenticación, navegación desde emails y enlaces compartidos.

El caso difícil: deep link + login

Si el usuario toca un enlace a una pantalla privada pero todavía no está autenticado, la aplicación debe recordar la intención, mostrar login y después continuar hacia la ruta original. Esto es un flujo de navegación, no simplemente un navigate() aislado.

Sección 12

Los errores clásicos de React Navigation

La mayoría de los problemas no vienen de la sintaxis: vienen de no entender la jerarquía.

Error 1 · "The action 'NAVIGATE' was not handled"

Normalmente significa que el navigator que recibió la acción no tiene una ruta con ese nombre, o que la ruta está dentro de un navigator hijo y estás intentando navegar desde el nivel equivocado. Revisá quién contiene realmente la ruta.

Error 2 · múltiples NavigationContainer

En una app normal debe existir un container raíz. Crear containers anidados puede generar árboles de navegación independientes y comportamientos inesperados.

Error 3 · nombres de rutas inconsistentes
<Stack.Screen name="TaskDetail" ... />

navigation.navigate('Detail') // ❌ no existe
Error 4 · usar params como estado global

Si diez pantallas necesitan leer y modificar el mismo usuario, pasar el usuario por params de una pantalla a otra no escala. Usá una fuente de estado apropiada.

Error 5 · poner todo en un único Stack

Al principio funciona. Después aparecen Home, Login, Settings, Profile, Detail, EditProfile, Modal y 25 pantallas más dentro de un mismo navigator. La solución no es crear un Stack gigante: hay que modelar la jerarquía de navegación.

Checklist de debugging
  • ¿La ruta existe realmente?
  • ¿Está en este navigator o en un hijo?
  • ¿Estoy llamando a navigate, push o replace intencionalmente?
  • ¿Los nombres de las rutas coinciden exactamente?
  • ¿Estoy creando accidentalmente otro NavigationContainer?
  • ¿El usuario tiene permiso/sesión para que esa ruta exista?
  • ¿El problema es de navegación o en realidad de layout/Safe Area?

Tipado con TypeScript

En un proyecto profesional, uno de los mayores beneficios de TypeScript es poder tipar los nombres de las rutas y sus parámetros. Así un typo como navigate('Detial') deja de ser un bug que descubrís al ejecutar la app. 

type HomeStackParamList = {
  Home: undefined
  Detail: { taskId: string }
  Edit: { taskId: string }
}

const Stack = createNativeStackNavigator<HomeStackParamList>()

// Ahora TypeScript conoce:
navigation.navigate('Detail', { taskId: 'abc' })

// Y rechaza:
navigation.navigate('Detail') // ❌ falta taskId
navigation.navigate('Unknown') // ❌ ruta inexistente
El objetivo de esta clase

No memorizar veinte métodos de navegación. El objetivo es poder mirar una aplicación y decidir: qué parte es Stack, qué parte es Tabs, qué parte es Drawer, dónde vive cada ruta, qué información necesita y quién es responsable de volver.
