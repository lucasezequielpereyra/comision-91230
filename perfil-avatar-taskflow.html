Sección 1

Expo ImagePicker: pedirle una foto al sistema operativo

En la web alcanza con un <input type="file">. En mobile, la galería es del sistema operativo: le pedimos que abra su propia interfaz y nos devuelva un archivo.

expo-image-picker es la librería estándar de Expo para eso. Resuelve tres cosas en Android y en iOS: permisos (preguntarle al usuario), interfaz nativa (la galería real del teléfono) y edición básica (el recorte cuadrado que necesita un avatar).

src/screens/profile/ProfileScreen.tsx
const pickImage = async () => {
  // 1. Sin permiso 'granted' no se puede abrir la galería
  const { status } = await ImagePicker.requestMediaLibraryPermissionsAsync()

  if (status !== 'granted') {
    Alert.alert(
      'Permisos requeridos',
      'Necesitamos acceso a tu galería para cambiar la foto de perfil.'
    )
    return
  }

  // 2. Selector nativo con recorte cuadrado para el avatar
  const result = await ImagePicker.launchImageLibraryAsync({
    mediaTypes: ['images'],
    allowsEditing: true,
    aspect: [1, 1],
    quality: 0.7,
  })

  // 3. Si el usuario canceló, no hay assets para leer
  if (result.canceled) return

  await savePhoto(result.assets[0].uri)
}

Las opciones del selector, una por una

OpciónValor en TaskFlowPara qué sirve
mediaTypes['images']Solo fotos, sin videos. El material muestra ImagePicker.MediaTypeOptions.Images: esa forma está deprecada en SDK 54 y se reemplaza por el array.
allowsEditingtrueAbre el editor nativo para recortar antes de confirmar.
aspect[1, 1]Recorte cuadrado, ideal para un círculo. Se aplica en Android; en iOS el recorte ya es siempre cuadrado.

¿Hace falta pedir permiso?

Según la documentación de Expo, para elegir imágenes de la galería no es obligatorio. Igual conviene pedirlo y manejar el 'denied' con un Alert: es lo que evalúa la entrega (“sin errores de permisos”) y el día que agregues videos o cámara, ya está resuelto.

El plugin expo-image-picker con photosPermission define el mensaje que ve el usuario en iOS. Se aplica en builds nativas (EAS / prebuild). En Expo Go vas a ver el texto de Expo Go.

Lo que recibe tu código

Error común: pensar que la foto ya está “en la nube”

La uri empieza con file:// y apunta a la caché de ese teléfono. Guardarla en Firestore alcanza para la entrega: la app la recuerda entre sesiones en el mismo dispositivo. En otro teléfono, o si el sistema limpia la caché, esa ruta ya no existe. Por eso la UI siempre necesita un fallback. En producción, el archivo se sube a Cloud Storage (sección 4).

Sección 2

Diseño del avatar: un círculo que no se deforma

En la web hay <img>, object-fit y border-radius: 50%. En React Native las piezas se parecen, pero tienen reglas propias.

source en lugar de src

Imagen remota o de archivo
source={{ uri: user.photoURL }}

Una uri (file:// o https://) necesita width y height explícitos. Sin eso se renderiza con altura 0.

Imagen local empaquetada
require('../../assets/avatar.webp')

Con require, Metro resuelve el archivo al compilar y conoce sus dimensiones. En TaskFlow es el fallbackAvatar.

La regla del círculo: radio = lado ÷ 2

borderRadius: '50%' puede dar óvalos dentro de contenedores Flexbox que no son perfectamente cuadrados. TaskFlow define el tamaño una vez y deriva el radio de esa constante: el perfil usa 88 → 44 y el header de la lista, 40 → 20.

src/screens/profile/ProfileScreen.tsx
// Para un círculo perfecto el borderRadius tiene que ser
// exactamente la mitad del lado; '50%' no es confiable en RN.
const AVATAR_SIZE = 88

avatar: {
  width: AVATAR_SIZE,
  height: AVATAR_SIZE,
  borderRadius: AVATAR_SIZE / 2
},

Tres estados que la pantalla tiene que resolver

Vacío

El usuario nunca eligió foto: photoURL === null. Se muestra fallbackAvatar o un círculo con la inicial del email.

Guardando

Mientras Firestore responde, isSaving pone un ActivityIndicator sobre el avatar y deshabilita el toque.

Error de carga

La uri guardada ya no existe (otro teléfono, caché limpia). onError vuelve al fallback.

Mejora sugerida: fallback cuando la imagen no carga

const [failed, setFailed] = useState(false)

<Image
  source={user?.photoURL && !failed ? { uri: user.photoURL } : fallbackAvatar}
  style={styles.avatar}
  onError={() => setFailed(true)}  // la ruta file:// ya no existe
/>
Área táctil de al menos 44×44

El badge de la cámara mide 28 px: solo sería difícil de tocar. En TaskFlow el TouchableOpacity envuelve todo el avatar (88×88), y el badge solo indica que se puede tocar.

¿Hace falta un cache-buster?

Con ImagePicker, cada selección genera un archivo con nombre nuevo, así que la uri cambia y no hay caché vieja. Con Storage y una ruta fija como avatars/{uid}/avatar.jpg, sí puede quedar la imagen vieja en caché: agregale una versión a la URL, por ejemplo url + '&v=' + Date.now() (con &, porque la URL de descarga ya trae ?alt=media).

Sección 3

Integración: la misma foto en toda la app

Si la foto solo vive en el useState de Perfil, al volver a Tareas el header muestra la anterior. La solución es un flujo circular: galería → Firestore → Redux → pantallas.

1 · La capa de datos: users/{uid}

src/services/profile/profileService.ts
// El perfil de cada usuario vive en un documento `users/{uid}`.
export const getUserProfile = async (userId: string): Promise<UserProfile | null> => {
  const snapshot = await getDoc(doc(db, 'users', userId))
  if (!snapshot.exists()) return null

  const data = snapshot.data()
  return { photoURL: data.photoURL ?? null }
}

export const updateUserPhoto = async (userId: string, photoURL: string) => {
  // setDoc con merge y no updateDoc: el documento del usuario
  // puede no existir todavía (el registro solo crea la cuenta en Auth).
  await setDoc(doc(db, 'users', userId), { photoURL }, { merge: true })
}
updateDoc vs. setDoc(…, { merge: true })

El ejemplo del material usa updateDoc. Con un usuario recién registrado falla con not-found (“No document to update”), porque createUserWithEmailAndPassword crea la cuenta en Auth pero no el documento en Firestore. setDoc con merge crea el documento la primera vez y después solo actualiza photoURL. Para las reglas, eso significa que la primera foto es un create y las siguientes son update.

2 · El estado global: setUserPhoto

src/features/auth/authSlice.ts
setUserPhoto: (state, action: PayloadAction<string | null>) => {
  if (state.user) {
    state.user.photoURL = action.payload
  }
},

3 · Guardar desde la pantalla

src/screens/profile/ProfileScreen.tsx
const savePhoto = async (photoURL: string) => {
  if (!user) return      // primero el guard...
  setIsSaving(true)        // ...después el loading

  try {
    // Firestore primero (persistencia entre sesiones)...
    await updateUserPhoto(user.uid, photoURL)

    // ...y Redux después: toda la UI suscripta al store se entera ya.
    dispatch(setUserPhoto(photoURL))
  } catch (error) {
    Alert.alert('Error', 'No se pudo guardar la foto. Probá de nuevo.')
  } finally {
    setIsSaving(false)
  }
}
El orden del guard importa

Si setIsSaving(true) va antes de if (!user) return, ese return sale sin pasar por el finally del try, y el spinner queda girando para siempre. Primero se valida y después se activa el estado de carga.

4 · Hidratar la foto al abrir la app

src/navigation/RootNavigator.tsx
onAuthStateChanged(auth, async (user) => {
  if (user) {
    dispatch(setUser({ uid: user.uid, email: user.email, displayName: user.displayName, photoURL: null }))

    // La foto vive en Firestore; se hidrata después de setUser
    // para no demorar la entrada a la app.
    try {
      const profile = await getUserProfile(user.uid)
      if (profile?.photoURL) dispatch(setUserPhoto(profile.photoURL))
    } catch (error) { /* sin foto: se ve el fallback */ }
  } else {
    dispatch(setUser(null))
  }
})
Sin prop drilling

ProfileScreen y TasksScreen están en tabs distintas y ninguna le pasa props a la otra. Las dos leen user.photoURL del mismo store.

Sin esperar a Firestore para entrar

setUser llega primero con photoURL: null: la navegación privada se monta ya y la foto aparece un instante después.

Sección 4

Reglas de Firebase para que el usuario pueda poner su avatar

El código ya está completo, pero en un proyecto de Firebase recién creado la foto no se guarda: Firestore arranca bloqueando todo lo que no esté permitido de forma explícita.

Sin reglas para users/{userId}, la llamada a updateUserPhoto termina en el catch con este error, y el usuario ve el Alert “No se pudo guardar la foto”: 

FirebaseError: Missing or insufficient permissions.   // error.code === 'permission-denied'
“Modo de producción”

La base se crea con allow read, write: if false;. Nada funciona hasta que publiques reglas propias: ni las tareas ni el avatar.

“Modo de prueba”

Permite todo hasta una fecha de vencimiento (request.time < timestamp.date(…)). Mientras dura, cualquiera puede leer o pisar los perfiles de otros; cuando vence, la app deja de funcionar.

Dónde se cargan

1

Consola de Firebase → Firestore Database → pestaña “Reglas”

Es el mismo proyecto que figura en projectId dentro de src/config/firebase.ts.

2

Reemplazá todo el contenido por el archivo de abajo

Incluye las reglas de tasks del módulo 7: si solo pegás el bloque de users, las tareas dejan de cargar.

3

Tocá “Publicar” y esperá alrededor de un minuto

Después cerrá y abrí la app. Si preferís la CLI: guardalo como firestore.rules y ejecutá firebase deploy --only firestore:rules.

firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isSignedIn() {
      return request.auth != null;
    }

    function isOwner(uid) {
      return isSignedIn() && request.auth.uid == uid;
    }

    // La uri de ImagePicker (file://...) o, en producción, una URL de Storage
    function isValidPhoto(value) {
      return value == null
        || (value is string && value.size() > 0 && value.size() <= 2048);
    }

    // ── Tareas (módulo 7) ────────────────────────────────
    match /tasks/{taskId} {
      allow read, delete: if isOwner(resource.data.userId);
      allow create: if isOwner(request.resource.data.userId);
      allow update: if isOwner(resource.data.userId)
        && request.resource.data.userId == resource.data.userId;
    }

    // ── Perfil y avatar (módulo 8) ───────────────────────
    match /users/{userId} {
      allow read: if isOwner(userId);

      // Primera foto: setDoc(merge) sobre un documento que no existe
      allow create: if isOwner(userId)
        && request.resource.data.keys().hasOnly(['photoURL'])
        && isValidPhoto(request.resource.data.photoURL);

      // Fotos siguientes: solo puede cambiar photoURL
      allow update: if isOwner(userId)
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['photoURL'])
        && isValidPhoto(request.resource.data.photoURL);

      allow delete: if false;
    }
  }
}

Qué protege cada condición del bloque users

CondiciónQué exigeQué evita
isOwner(userId)Sesión iniciada y request.auth.uid igual al ID del documento.Que alguien sin sesión, o con otra cuenta, lea o cambie tu foto.
keys().hasOnly(['photoURL'])Al crear, el documento solo puede tener photoURL.Que un cliente modificado se cree el perfil con campos como role: 'admin'.
diff(…).affectedKeys().hasOnly(['photoURL'])Al actualizar, el único campo que cambia es photoURL.Lo mismo en updates. keys() no sirve acá: incluye también los campos que no cambiaron.
isValidPhoto(…)Texto de 1 a 2048 caracteres, o null.Números, objetos o textos gigantes guardados en photoURL.
allow delete: if falseNadie borra perfiles desde la app.Borrados accidentales. Si más adelante hace falta, se habilita a propósito.
Cuando el perfil crezca

Si agregás displayName o bio al documento, sumalos a las dos listas: hasOnly(['photoURL', 'displayName']). Si no, las reglas van a rechazar esa escritura, y está bien que lo hagan: es la lista de campos permitidos.

Para producción: la foto en Cloud Storage

La entrega guarda la uri local. El paso siguiente es subir el archivo a Cloud Storage y guardar en photoURL la URL https:// que devuelve getDownloadURL. Las reglas de Firestore no cambian (isValidPhoto acepta cualquier texto válido), pero Storage necesita las suyas.

Storage requiere plan Blaze

Desde febrero de 2026, usar un bucket de Cloud Storage for Firebase exige tener el proyecto en el plan Blaze (pago por uso, con capa gratuita). Es una razón práctica para que la entrega del curso no dependa de Storage.

storage.rules · opcional, no lo usa el código actual
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /avatars/{userId}/{fileName} {
      // Cualquier usuario con sesión puede ver avatares
      allow read: if request.auth != null;

      // Solo el dueño sube: imagen de menos de 2 MB
      allow create, update: if request.auth != null
        && request.auth.uid == userId
        && request.resource.size < 2 * 1024 * 1024
        && request.resource.contentType.matches('image/.*');

      // En un delete no hay request.resource: se valida aparte
      allow delete: if request.auth != null
        && request.auth.uid == userId;
    }
  }
}
Boceto del lado de la app · no está en el repo
import { getStorage, ref, uploadBytes, getDownloadURL } from 'firebase/storage'

const storage = getStorage(app)

export const uploadAvatar = async (userId: string, uri: string) => {
  const blob = await (await fetch(uri)).blob()     // file:// → Blob
  const avatarRef = ref(storage, `avatars/${userId}/avatar.jpg`)

  await uploadBytes(avatarRef, blob, { contentType: 'image/jpeg' })
  return getDownloadURL(avatarRef)                  // https://... → photoURL
}
