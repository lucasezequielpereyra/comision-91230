Sección 1

El pipeline: de datos a píxeles

Antes de tocar una sola prop de FlatList, hay que ver el camino completo que recorre un dato hasta convertirse en algo que se toca con el dedo.

La confusión más común al venir de la web es pensar que React Native dibuja HTML dentro de un navegador escondido. No es así. Tu código JavaScript describe qué quiere ver, y la plataforma construye componentes nativos reales: un UIView en iOS, un android.view en Android. Entre esos dos mundos hay una frontera, y todo lo que aprendemos hoy existe para cruzarla lo menos posible.

La frase para llevarse de esta sección

La interfaz no se dibuja: se declara. Vos no le decís al teléfono "poné un rectángulo acá"; le decís "dados estos datos, así se ve la pantalla". Si los datos cambian, la pantalla cambia sola.

Sección 2

map(): la fábrica de componentes

El paso 2 del pipeline en detalle: cómo se transforma cada dato en su representación visual.

Cuando arrancamos, tendemos a escribir la interfaz de forma estática: si hay tres tareas, escribimos tres tarjetas a mano. Funciona hasta que el usuario tiene cien tareas. O ninguna.

La alternativa es pensar en proyección de datos. Imaginá map() como una línea de ensamblaje: por un lado entra materia prima (un objeto con un título y una fecha), la máquina la envuelve en una estructura visual —un borde, un botón, un estilo— y por el otro lado sale el producto terminado: una tarjeta lista para tocar.

Estático — no escala
<Tarea title="Comprar café" />
<Tarea title="Revisar PR" />
<Tarea title="Llamar al médico" />

// ¿y si hay 100? ¿y si hay 0?
// ¿y si el usuario agrega una?
Proyectado — escala solo
{tasks.map(task => (
  <Tarea
    key={task.id}
    title={task.title}
  />
))}

// 0, 3 o 10.000: el mismo código

Ese cambio de mentalidad es todo: dejamos de escribir componentes y empezamos a escribir una plantilla más una fuente de datos. Agregar una tarea al array hace aparecer la tarjeta; quitarla la hace desaparecer. Nunca tocamos la pantalla directamente.

Un detalle que confunde: for no sirve acá

Dentro del JSX necesitamos una expresión que devuelva un valor. Un for tradicional es una sentencia: no devuelve nada. map() sí devuelve un array nuevo, y React sabe renderizar un array de elementos. Por eso el patrón es siempre map, no for.

Sección 3

Las key: el DNI de cada componente

El concepto más incomprendido de React, y la causa del bug más difícil de rastrear que van a encontrar en toda la cursada.

Todos vimos alguna vez ese warning amarillo: "Each child in a list should have a unique key prop". La reacción típica es callarlo poniendo key={index} y seguir. Vamos a ver exactamente qué se rompe cuando hacemos eso.

Primero, lo importante: la key no es para vos. Nunca la vas a leer en tu código. Es para el algoritmo de reconciliación de React, que necesita responder una pregunta cada vez que la lista cambia: "este componente que tengo en pantalla, ¿es el mismo que antes, o es otro distinto?"

La respuesta importa porque los componentes tienen estado interno —un checkbox marcado, el texto a medio escribir en un input, una animación a mitad de camino. Si React se equivoca de identidad, ese estado se le queda pegado al componente equivocado.

Demo en vivo

Probalo vos: marcá un check y borrá una tarea de arriba

El check es estado interno del componente, no del dato — igual que un input a medio escribir. Cambiá la estrategia de key y repetí la operación.

Las dos keys que nunca hay que usar
  • Math.random() — genera una key distinta en cada render. React concluye que todos los elementos son nuevos siempre: destruye y recrea la lista entera en cada cambio. Adiós rendimiento, adiós foco del teclado.
  • El índice del array — el caso que acabamos de ver. Solo es aceptable si la lista es estática: nunca se reordena, nunca se filtra, nunca se borra del medio. En TaskFlow no aplica.
La regla de oro

Un ID único que venga de la fuente de datos (base de datos, API) o generado una sola vez en el momento de crear el elemento —un UUID, o un timestamp más un sufijo aleatorio. La clave está en cuándo se genera: al crear el dato, no al renderizarlo.

Sección 4

Inmutabilidad: por qué map y nunca push

El segundo bug clásico: "marco la tarea como completada, el estado cambia… pero la pantalla no se entera".

React no inspecciona el contenido de tus objetos para ver si algo cambió — sería carísimo hacerlo en cada render. Lo que hace es comparar referencias: ¿el array que me pasás ahora es el mismo objeto en memoria que el que tenía antes? Si es el mismo, asume que nada cambió y no vuelve a renderizar.

Métodos que mutan — evitar sobre el estado
  • push() / pop()
  • splice()
  • sort() / reverse()
  • Asignación directa: tasks[i].done = true
Métodos que devuelven copia — usar estos
  • map() — modificar un elemento
  • filter() — eliminar
  • [nuevo, ...prev] — agregar
  • { ...obj, campo: valor } — un objeto
¿Y si necesito ordenar?

sort() muta el array sobre el que se llama. La forma segura es copiar primero: [...tasks].sort(...). Es un error muy común porque sort además devuelve el array — parece que funciona como map, pero devuelve el mismo array que mutó.

Sección 5

Virtualización: qué hace FlatList que ScrollView no

La razón por la que existe un componente de lista específico en React Native, y por qué en la web nunca lo necesitamos.

En la web podemos meter mil <div> en el DOM y el navegador se las arregla. En móvil, cada elemento se convierte en una vista nativa real, con su costo de memoria y de creación. Mil tareas en un ScrollView son mil vistas nativas construidas antes de que el usuario vea la primera.

FlatList resuelve esto con windowing: mantiene montadas solo las filas visibles más un margen a cada lado, y a medida que hacés scroll recicla las que salen de pantalla para mostrar las que entran. La lista puede tener diez mil ítems: en memoria siempre hay una docena.

Cuándo sí conviene ScrollView

Cuando el contenido es corto y de longitud conocida: un formulario largo, una pantalla de detalle, los términos y condiciones. Ahí la virtualización no aporta nada y agrega complejidad. La regla práctica: si la cantidad de elementos la definís vos, ScrollView; si la define el usuario o el servidor, FlatList.

Sección 6

Anatomía de una FlatList bien hecha

Cada prop, y qué problema concreto resuelve.

const keyExtractor = (item) => item.id   // ① fuera del componente

export default function TaskList({ tasks, onToggle, onSelect }) {

  const renderItem = useCallback(                      // ② identidad estable
    ({ item }) => <TaskItem task={item} onToggle={onToggle} onPress={onSelect} />,
    [onToggle, onSelect]
  )

  return (
    <FlatList
      data={tasks}                        // ③ la fuente de verdad
      keyExtractor={keyExtractor}         // ④ identidad de cada fila
      renderItem={renderItem}             // ⑤ la plantilla
      ListEmptyComponent={EmptyState}     // ⑥ nunca una pantalla en blanco
      contentContainerStyle={{ flexGrow: 1 }}

      initialNumToRender={8}              // ⑦ tuning de virtualización
      windowSize={7}
      maxToRenderPerBatch={8}
    />
  )
}
PropQué problema resuelve
① keyExtractor hoisted No depende de props ni estado, así que no hay razón para recrear la función en cada render. Definida a nivel de módulo, se crea una sola vez en toda la vida de la app.
② renderItem con useCallback Si la definís inline, cada render del screen crea una función nueva. FlatList ve una prop distinta y asume que todo cambió: repinta las filas al pedo.
③ data El array. Cuando cambia de referencia, la lista se actualiza — de ahí la importancia de la sección anterior.
④ keyExtractor El equivalente de key en FlatList. Todo lo de la sección 3 aplica igual.
⑤ renderItem Recibe { item, index, separators }. Desestructurar { item } y delegar en un componente aparte mantiene la fila liviana.
⑥ ListEmptyComponent Se renderiza solo cuando data está vacío. Resuelve el estado vacío sin un ternario en el JSX. Con flexGrow: 1 se puede centrar verticalmente.
⑦ Tuning initialNumToRender: cuántas filas en el primer paint (las que llenan la pantalla). windowSize: el margen, medido en pantallas. maxToRenderPerBatch: cuántas filas por tanda al scrollear — tandas chicas mantienen la UI respondiendo.
El componente de fila: memo + props estables

La otra mitad del trabajo está en TaskItem. Envolverlo en memo() hace que se saltee el render si sus props no cambiaron — y gracias al map inmutable de la sección anterior, las filas que no tocamos reciben exactamente el mismo objeto y se saltean de verdad.

Ojo: memo solo funciona si las funciones que le pasás también son estables. Un onPress={() => ...} inline crea una función nueva por render y anula el memo por completo. Por eso los handlers viven en useCallback.

Sobre getItemLayout

Es la optimización más potente —le permite a FlatList calcular posiciones sin medir cada fila— pero exige que todas las filas midan exactamente lo mismo. Si el número que le pasás no coincide con la altura real, aparecen huecos en blanco al scrollear. Con tarjetas de altura variable, como las de TaskFlow, es mejor no usarla.

Sección 7

El patrón Master-Detail

La lista es media aplicación. La otra media es lo que pasa cuando el usuario toca una fila.

Spotify, WhatsApp, Gmail, Mercado Libre: todas son, en el fondo, una lista que lleva a un detalle. La clave conceptual es que lista y detalle son dos vistas del mismo dato: en la lista mostramos una versión resumida (título, hora), en el detalle el objeto completo (descripción, categoría, historial). 

// La navegación simulada, completa
const [tasks, setTasks] = useState([])
const [selectedTask, setSelectedTask] = useState(null)

if (selectedTask) {
  return <TaskDetail task={selectedTask} onBack={() => setSelectedTask(null)} />
}

return (
  <SafeAreaView>
    <TaskForm onAdd={addTask} />
    <FlatList
      data={tasks}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <TouchableOpacity onPress={() => setSelectedTask(item)}>
          <Text>{item.title}</Text>
        </TouchableOpacity>
      )}
      ListEmptyComponent={EmptyState}
    />
  </SafeAreaView>
)
El detalle que se pasa por alto

Si el detalle recibe una copia del objeto y desde ahí marcás la tarea como completada, hay que sincronizar los dos lugares: el array y la copia seleccionada. Es exactamente el problema que desaparece cuando pasás solo el id y el detalle lee siempre de la fuente de verdad — y es la razón por la que ese es el estándar profesional.

Sección 8

La lista rota: los tres bugs clásicos

El ejercicio de debugging de la clase en vivo. Este código tiene tres problemas. Antes de seguir leyendo: ¿cuáles? 

export default function TaskList() {
  const [tasks, setTasks] = useState(INITIAL_TASKS)

  const toggle = (index) => {
    tasks[index].completed = !tasks[index].completed
    setTasks(tasks)
  }

  return (
    <FlatList
      data={tasks}
      renderItem={({ item, index }) => (
        <TouchableOpacity onPress={() => toggle(index)}>
          <Text>{item.title}</Text>
        </TouchableOpacity>
      )}
    />
    // ← falta algo acá
  )
}
Bug 1 · Mutación directa del estado

tasks[index].completed = ... modifica el objeto en su lugar, y setTasks(tasks) pasa la misma referencia. React compara, ve que es el mismo array y no re-renderiza. Síntoma: tocás la tarea y no pasa absolutamente nada. El dato cambió, la pantalla no. Fix: setTasks(prev => prev.map(t => t.id === id ? {...t, completed: !t.completed} : t))

Bug 2 · Falta keyExtractor

Sin él, FlatList cae al índice como identidad. Síntoma: warning en consola, y al borrar o reordenar, el estado interno de las filas se corre —el bug de la sección 3. Fix: keyExtractor={(item) => item.id}

Bug 3 · renderItem anónimo e inline

Se recrea en cada render, así que FlatList recibe siempre una prop nueva y no puede optimizar nada. Síntoma: scroll con tirones cuando la lista crece; no se nota con 5 ítems, sí con 500. Fix: extraerlo a useCallback y mover la fila a un componente con memo.

Bonus: no hay ListEmptyComponent. Si el usuario borra todas las tareas, se queda mirando una pantalla en blanco sin entender si la app se rompió o simplemente no hay nada.

La pista, si nadie lo encuentra: referential identity

Los tres bugs son la misma idea vista desde tres ángulos. React razona por identidad de referencia: qué objeto es el mismo que antes y qué objeto es nuevo. Mutar rompe esa señal, el índice la falsifica, y una función inline la destruye en cada render.

Checklist antes de entregar el checkpoint

  • Con el array vacío se ve el EmptyState, nunca una pantalla en blanco.
  • Una tarea creada desde el formulario aparece en la lista y su detalle se abre.
  • keyExtractor usa un ID único, no el índice.
  • El toggle genera un array nuevo con .map(), sin mutar el original.
  • El botón de volver deja la app exactamente como estaba.
  • La consola de Metro no muestra ningún warning de React durante la interacción.
  • El detalle usa StyleSheet y respeta la línea visual de los módulos previos.
  • El repositorio está limpio, en la rama solicitada.
